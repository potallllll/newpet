## 1. 当前结论

- 客户端 V1.0 业务基线已确认；店员端本批业务规则已确认，当前仍可继续讨论后续页面和技术细节。
- 所有门店业务操作均不设置老板审批或二次审批。只有消费退款、充值退款和免单的原因必填；其他原因均选填。每次成功修改自动记录操作人、服务端时间、修改前值和修改后值。
- 消费结算成功后，最终应收、实收、付款拆分和收款时间锁定。少收在原单追加补收，多收或不应收走退款；不提供更正收款或直接覆盖余额。
- 不提供“修改余额”。已入账充值需要退还时，只能从原充值记录发起充值退款。
- 优惠券和活动券在结算时选择，由服务端校验并计算优惠，结算成功后自动核销、关联原单。V1 积分商城只兑换实物，不兑换券。
- V1 不做跨店顾客／宠物档案或服务护理历史导入。跨店顾客风险只按认证手机号匹配，需双方门店授权、顾客分项同意、真实业务触发、每店同顾客每自然月最多3次及平台审核（`customer_risk.review`）；顾客端不显示风险记录，也不提供自助申诉，异议统一联系客服。
- 同一平台账号同一时刻只能归属一家有效经营门店；已经是某店老板或员工时，不能同时成为其他门店老板或员工。
- 门店日常经营和老板设置全部在店员小程序；网页后台只供平台使用。

## 2. 本批关键业务口径

### 服务、寄养与订单

- 快速开单完成必要检查并提交后直接开始服务；普通预约到店后仍由员工手动开始。发现同次有效预约时提供跳到原预约，取消／中止后的新单同样按入口决定开始方式。
- 顾客线下合并转账后由店员逐张打开独立原单，登记本单实收份额，不开放跨业务混结收银台；已线下收款交货的超时商品需求允许关联补记；常规金额录错由门店按原单自助追加补收／消费退款；仅门店停用，或店员端异常使该笔业务确实无法自助时，由平台沿05§6直接修复；财务代办复用同一套补收／退款。详见03d§11.2～11.3与03e§13.1，相关契约须先登记。
- 正式服务分类唯一为“洗护／美容／其他”。服务项目管理、临时开单和会员开单直接共用同一分类；护理归“其他”，商品和寄养保持独立业务，不建立第二套分类或映射。两种开单均须选择该分类并填写本单价格，只在顾客资料取得方式上不同。
- 熟客查档后可带入开单／寄养，原开单／入住／结算只使用小程序前端本地临时缓存，提交前查原单或请求，成功或退出即清空；消费争议仍无草稿。洗前六项用快捷标签，寄养自带物品可选多选，预约管理有今日时段视图，服务／商品列表可置顶常用项。顾客当前服务显示下一步、订单账单区分已登记实收和未登记，已完成洗美可再次预约。洗护及符合条件的驱虫商品可由门店选填单次14／30天普通提醒，详见04、03a／03d／03e／03f／03i。
- 店员端底栏为“工作台／业务／快捷入口／客户／我的”。工作台只保留当天待处理、服务中、异常与临期，不展示快捷操作；快捷入口统一承载临时开单、会员开单、客户查询、寄养入住。洗护／美容办理列表归“业务 → 洗美”。
- 补图和修改普通说明不发送通知；除此之外的服务结果错误一律重新开单，不覆盖原服务事实。
- 寄养客户端状态统一为“寄养中／待结算／已完成／已取消”。计费沿凌晨3点过夜规则、实际离店结算；照护时间轴只保留“喂食／遛狗／清扫笼子／其他”，每条可选填一句说明。
- 首页消费争议首批使用10b§7紧凑卡，固定“附近门店”“宠物食品”两个入口、最多一条摘要，详细视觉稿在 Stage 10 锁定。
- 店员端五项底栏和各主菜单顺序按04§3.0／3.2锁定；“老板管理”入口及八项子菜单按04§3.0.4锁定。单手点按布局和共享视觉基线见[店员端页面布局与老板菜单排序锁定清单](10d-staff-layout-and-owner-menu-checklist.md)。
- AI 洗护报告由顾客主动发起，同一订单仅成功生成一次。补图只更新展示对比图，原报告保留，不重跑或再次消耗广告资格。
- 原充值的赠送金或赠券任一已使用即阻断自动计算。本店老板与顾客协商后，从原充值单手动输入实际退还本金，原因必填，系统自动审计，见03c§4.3。
- 邀请码活动在本店顾客消费历史读取原兑换及原券实例，成功核销关联原订单；展示 DTO 后续登记，不另造交易。
- 上门喂养入口与状态以03j为准；到结束日期自动变为“已结束”。附近没有服务门店时提示“附近暂无服务门店”后结束；定位失败时让顾客手动选区。当前负责门店账号停用时，未结束需求及待办自动转给最近的其他有效门店，保留原接单人和历史；新店重新确认后可查看双方联系方式，无候选时停止继续对接。
- 待办归门店，谁处理就记谁，不做领取或转交。历史订单没有业绩归属时统一归本店老板，业绩按实际实收减已确认退款计算。

### 投诉、风险与平台处理

- 消费争议只提示联系客服，不保留“申诉”入口或新申诉状态。未入驻门店被投诉时标记“未入驻”，门店入驻后可补回应。
- 同一用户可对同一食品批次再次投诉，但必须提供新证据。集中反馈再次触发时，从本次触发时间重新计算提示有效期。
- 第三方证据只分高／中／低三档，由持有 `evidence.review` 的 Platform Super Admin 人工判断；不得由算法自动定责。
- 食品问题由平台直接联系厂家并在Web后台处理；门店只收到知悉通知，不参与前置核实、厂家沟通或回信维护。厂家回信由平台录入并审核，通过即算回应，不设期限。
- 食品问题热度只显示“低／中／高”三档。积分实物异常由平台在原兑换单处理，门店没有操作入口。

### 页面、身份与权限

- 客户端首页禁止顶部品牌／生活方式Banner，只保留唯一门店栏；商品标题使用“本店推荐”。首页消费争议使用简版卡片，精确视觉在阶段10继续收口。
- 员工可查看本店顾客完整手机号；营业执照只允许本店老板和平台管理员查看。
- 顾客手机号相同按同一平台账号识别；同店发现资料冲突时提示处理，不自动合并两个既有业务对象。
- 通知只有普通通知和重要通知两档；已退役的“宠物好友邀请”消息类型不得恢复。

### 广告与积分实物

- 启动广告资源最多等待2秒；自定义图片展示3秒并始终允许跳过。超时、失败或无填充直接进入原目标业务。
- 积分实物领取门店停用时，系统自动取消原兑换、退回积分并发送重要通知，不让顾客改选门店。

## 5. 开发批次与后续阶段边界

首批优先打通客户端＋店员端小程序核心闭环，先覆盖预约、开单、洗美、寄养、结算等社区小店高频路径。双端核心验收通过后接入 Web，验证 Web 管理页面不可用时高频路径仍能从双端办理。阶段05完整 Web 平台后台延后，低频异常通过现有客服／平台人工承接。发布顺序见[05 §8](05-platform-web-admin.md)。

**技术栈已确认**。客户端和店员端微信小程序统一采用 uni-app（Vue 3），后端采用 Java（Spring Boot），数据库采用 MySQL 8.0，缓存采用 Redis。

**仓库与 AppID 规则已确认**。后端、客户端小程序、店员端小程序、平台 Web 和文档采用单仓。开发可先用测试号或占位值 `YOUR_CUSTOMER_APPID`；真实微信能力联调用有效测试 AppID，正式上线前替换为对应的正式 AppID 并完成正式配置验收。

正式开发准入仍待关闭 DEC-EXEC-01／02 的其余事项，并须取得开工授权。实际开发仓库与分支、细化批次、实际联调配置、环境和部署目标见[执行标准](execution/deepseek-execution-standard.md)。

下列内容不是本批未拍板业务规则，而是后续阶段的设计工作：

- 平台后台的账号生命周期、页面动作权限标识、队列／文件与受限修复接口契约，以05及后续阶段为依据；
- [08 首批契约](08-api-and-authorization.md) 明确的依赖事项，以及后续批次的数据库、API／DTO、事件、缓存、迁移、幂等、并发与补偿设计；
- 首页消费争议简版卡片的阶段10精确视觉；
- 生产微信广告、支付、消息模板和真实平台能力接入及验收。

任何实现不得用“技术细节尚未设计”为由恢复已删除流程，也不得把临时H5或历史文档当作正式需求。
