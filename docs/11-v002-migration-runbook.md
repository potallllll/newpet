# 11｜V002 增量迁移与回退手册

迁移顺序为[原版 V001](../backend/src/main/resources/db/migration/V001__newpet_batch_a_core.sql) → [V002](../backend/src/main/resources/db/migration/V002__newpet_batch_a_runtime_foundations.sql)。V001 的 SHA-256 固定为 `c340be6abd87501f07f57a169bb5895162f7f4bf46505196f7188eed9392f632`。V001 与 V002 各在同一个迁移目录建档，脚本直接核对这一份 V001。工程初始化复用原文件和版本；已有 Flyway 历史的环境先核对已登记版本与校验和。

## 2. 升级部署步骤

1. 确认阶段 09 V001 的 SHA、Flyway history 和目标版本；以合成数据或授权脱敏副本跑迁移。检查四张 V001 表现有索引名称、容量、DDL 磁盘占用和长事务，测 DDL 时间与锁等待。四个 ALTER 仅增加必要索引和带默认 1 的代次，保留 V001 记录、身份、原状态和金额。V002 R3 在 MySQL 8.0 与 8.4 已验证；目标托管 8.0 的锁、权限与 Flyway 实际运行在阶段 12 验收。已应用任何预发布 V002 的环境先查迁移历史，使用全新隔离库或经批准的前向迁移处理，禁止覆盖 Flyway 历史。
2. 建立带 binlog 定位的可恢复备份，部署变更期间暂停新写入口和 Worker；对单条 MySQL DDL 设置 5 秒元数据锁等待上限，超时以实际阻塞定位。Flyway 由唯一迁移作业运行；API 常规账号无 DDL 权限。迁移成功后用结构指纹、约束和业务基线计数核对，滚动更新 API 与 Worker，待数据库及授权配置验证后放开写入。
3. 默认所有新能力关闭。通过管理员受控流程登记各环境的 AppID、受众和已核实开放平台命名空间。对已验证的旧 AppID 绑定可补记可信分组，无法证明的一律保留旧绑定和空分组。启用 V002 会话时重新登录，旧 Redis 会话不得倒灌。配置证据首先在测试环境取证。
4. V002 为门头声明类型和大小追加 JPEG／PNG 与 3 MiB 约束，执照保持 JPEG／PNG 与 10 MiB，其他用途按其自己的规则。门头比例和文件实际类型由上传校验阶段读取文件验证。媒体历史按业务表、可信私有对象版本、上传主体和实际资源归属追溯。只有确认映射才双写原业务引用及 V002 挂接关系。无法核实的旧路径继续保留 V001 原引用供受控排查，前端不可见，不直接重用可访问旧 URL。媒体上线前清查公开桶与旧下载路径、撤销遗留公开访问。
5. 历史邀请码只有摘要，不能重构原码。原合法未过期码仍按摘要核验；曾成功发码的同键请求只返回原事实和现有失败提示（密封载荷不可用时用 `409 STATE_CONFLICT`），无需生成新码。成功的新发码同时保存密封记录。

## 3. 密封及重放

- 发码生成足够熵的随机秘密，查找摘要与加密密钥在不同域。保留现有 V001 规定的 12 小时入职码、72 小时顾客活动码及唯一使用次数。原券／权益领取后有效期仍依现有业务规则。
- 使用 envelope encryption。每条发码生成独立 DEK，AES-256-GCM、96 位 nonce、128 位 tag。AAD 采用带版本的确定性编码，覆盖环境、服务器实际店铺、创建者、原类型与 ID、幂等记录 ID、原截止与密封格式。KMS 的 key ID/version 和包装 DEK 随密文存放，不存明文 DEK。调用 KMS 工序先取 DEK，在本地事务内完成密封写入，提交后才返回明文。CI 和运行身份按用途隔离 KMS 授权。轮换时保留未到期旧版本的解密权限，过期后按 KMS 政策退役。
- 重放先验当前角色、原对象、请求摘要及同一演员归属，再解密同一份原值。截止到达后删除密文并保留成功回执，不重置有效期。原记录已用、权限被撤销或 KMS 暂不可用时仅按当前可见状态或稳定错误返回。KMS 失败时原事务整体失败或重放失败，不能以新码替代遗漏结果。
- 挑战上下文使用独立用途密钥和版本，KMS 环境绑定一致。MySQL 挑战过期后每分钟清理；保留父行直到其子挑战也失效并清理完毕。保留中的备份仍可能含密封历史，恢复时先处理纪元和原截止，备份到期按备份策略销毁。微信证明的重新发起和结果查询按阶段 08 执行。

## 4. 回退与半完成处置

- 仅应用回退：先停相关能力并阻断新任务，保留所有 V002 行，回退到声明兼容 V002 的旧应用版本。旧应用不得启用会话、媒体旧入口或发码重放。迁移后已有数据用原接口继续读取。数据库版本前进，按事故处理流程补写迁移而非自动回退字段。
- 每条 MySQL DDL 独立提交。失败时阻止新版本上线，记录已经成功的 DDL，现场检查表、唯一约束、历史及保有的数据。未有新写的独立环境可从迁移前快照恢复再完整重跑；生产需按差异与数据事实设计只向前修复，复跑全部探针和 Flyway validate。处理迁移记录不替代实际结构核验。
- 全库回退前隔离写入和外部渠道，按备份恢复手册检查恢复点后的原单、权限和外部结果。禁用旧会话纪元及旧链接，重放需核实的历史事实由独立恢复流程确认。
