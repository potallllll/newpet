本文与 [OpenAPI 0.3.0](../contracts/openapi.batch-a.json) 是首批客户端与店员端的正式契约。已确认接口按本版执行。§9 的依赖条件及 §10 的联调和开发准入仍适用。0.3.0 收紧了部分请求、拆分预约读 DTO，并增加响应头及筛选声明。联调端须用本版本重新生成 API 类型。URL 前缀仍为 `/api/v1`。

## 1. 本批范围与单仓落位

- 首批打通同一套业务事实上的顾客小程序和店员小程序。主路径为微信认证与当前角色识别，顾客预约和门店确认或改期，服务开单与状态推进，逐宠寄养及分批结算，商品需求和库存，原单记账、免单、退款，顾客回看。钱包、选券、必要站内通知按原需求联动。OpenAPI 用 x-iteration 标记 A1_CORE 首轮主链、A2_ENABLER 支撑和 A_DEPENDENT 有依赖能力。三层划分是联调顺序提议。
- 契约同时登记支撑路径，例如老板设置、员工入职与失效、商品入库、券赠送、邀请码、媒体与 AI 报告。核心路径先验收。微信、媒体、AI、凭证和其他有条件路径按 §10 开放。阶段 05 平台 Web、跨店顾客风险审核、消费争议、积分总仓、上门喂养及广告配置按各正式批次接入。
- 单仓从仓库根目录统一使用 `apps/customer-miniapp/`（顾客端）、`apps/staff-miniapp/`（店员端）、`apps/platform-web/`（平台 Web）、`backend/`（Spring Boot）、`contracts/`（OpenAPI 与契约矩阵）和 `docs/`（正式文档）。两端和后端共用 `contracts/openapi.batch-a.json`。`YOUR_CUSTOMER_APPID` 为开发配置占位，真实微信联调用有效测试 AppID，上线各端使用对应正式 AppID。
- 本文件说明业务及鉴权。[授权矩阵](../contracts/authorization-matrix.csv) 给出逐端点角色、对象、版本和权限。[字段追踪](../contracts/field-trace.csv) 给出 DTO 的逻辑字段及物理映射，[参数追踪](../contracts/parameter-trace.csv) 单列 HTTP Header 与查询参数。[验收矩阵](08-acceptance-matrix.md) 列出服务端联测用例，[验证记录](08-contract-verification.md) 保存已执行的静态检查。OpenAPI `security` 描述凭证形式，`x-access` 描述服务端业务权限。
- 本稿采用 GitHub 已同步的 R09-01。物理层沿用已通过 MySQL 8.0 与 8.4 空库探针的 V001。API 视图、工程字段、未决映射与现有列的差异见 §9。 [正式状态](https://github.com/potallllll/newpet/blob/2227fc03a698ee8f1180e04a4aa93c7c6bfe6ec1/docs/REQUIREMENTS-STATUS.md) · [字段注册表](https://github.com/potallllll/newpet/blob/2227fc03a698ee8f1180e04a4aa93c7c6bfe6ec1/docs/FIELD-REGISTRY.md)

## 2. HTTP 通用约定

| 主题 | 契约 |
|---|---|
| 路径 | 统一 /api/v1。/stores 为公开资料；/customer/stores/{store_id} 为本人指定门店业务；/staff 为当前有效任职门店；/owner 另加老板资格；平台 Web 独立鉴权。 |
| 标识和金额 | 稳定 ID、资源版本用十进制字符串，服务端校验 BIGINT UNSIGNED 范围。金额用精确两位小数的字符串，Java BigDecimal 对账。final_receivable_amount 未确定时允许返回 null，零只表示已确定为零。 |
| 时间 | 输入 RFC3339 带时区，响应 UTC；经营分组与寄养截点按 Asia/Shanghai。付款、退款实际发生时间与服务端录入时间分开。服务开始、发送、审计与签发时间由服务端产生。时间条件在业务事务里重算。 |
| 结果 | 有记录的动作返回 200/201，AI 已接受异步任务可返回 202，退出当前会话等无响应体动作返回 204。普通结果最外层 data、request_id；错误采用 application/problem+json，含稳定 code 和 request_id。 |
| 分页 | 列表 cursor 绑定端、本人、门店、业务筛选及排序键；稳定排序同刻以 ID 补序。切店、变更过滤或失效游标重新获取。游客目录只见公开投影。顾客查档保留 `query`，商品搜索保留 `q`。两者适用于各自既有路由。 |
| 输入与回包 | 写入按显式字段白名单，未知属性拒绝。操作人、受众、授权店、资产归属、内部余额拆分、事件及最终状态由后台确定。顾客端响应使用单独 DTO，内部备注、充值成本、证照、工作人员审计、付款本金／赠送拆分和风险隐私由字段白名单隔离。 |
| 鉴权失败 | 401 为凭证缺失、无效或会话已失效。当前受众不匹配或角色权限不足可返回 403。查找跨店、非本人或没有可见性的对象统一 404，返回体与真实不存在保持同样形状。 |
| 业务失败 | 400 协议错误。409 为状态／版本／幂等冲突；只有仍有权的请求可以返回当前版本。422 为金额、库存、营业时间、检查或其他业务前置不满足。429 为限频。500 表示意外内部错误，使用通用 `INTERNAL_ERROR`、请求编号和脱敏消息。503 表示依赖暂不可用或提交结果待核对。 |
| 缓存与日志 | 认证及所有私有或用户相关端点，成功和失败响应均带 `Cache-Control: no-store`。日志保留 request_id 和必要的脱敏事件，屏蔽裸凭证、完整手机号、微信原始标识、发券码、私有链接及原始证明。 |

客户端可基于稳定业务错误显示正常友好提示。WECHAT 依赖失败保留登录状态真实结果。业务超时或网络断开时先用原对象与同一个 Idempotency-Key 查询或重试，后续动作要先确认是否实际成功。

## 3. 身份、会话与授权顺序

### 3.1 微信登录和换绑

1. 两端调用微信登录得到短码。交换入口 X-Miniapp-Client 只用于选择后端保存的对应 AppID 配置。受众由服务端完成可信交换确定；后续请求重验所发凭证的受众。凭证不跨端通用。两端复用稳定 Platform User，前端资料和传入角色均不参与身份判断。
2. 微信绑定已有有效认证手机号时直接返回 authenticated。否则发 mobile_required 的一次性短期挑战。用微信授权手机号凭证完成服务端验真，归一化后查唯一 Platform User。认证前不泄露绑定信息。有效经营身份是默认进入店员界面的依据。顾客小程序看到本人合法的店员入口提示后，在对应 AppID 下重新换取会话，流程按真机准入验证。
3. 认证手机号已由另一微信绑定时，发 rebind_required 及对应挑战。两端显示“手机号异常”“该手机号已绑定其他微信，是否换绑？”。选择更换号码重新认证新的手机号；退出保留原关系。冲突提示不回传旧微信、姓名、历史、门店或资产。
4. 换绑只有在当前手机号认证成功并明确确认后执行。锁原 User、绑定关系与版本，沿用原 ID、员工归属、Customer、订单与余额。在同一 MySQL 事务推进 auth_version、迁移绑定、审计。下一请求读最新版本，旧微信两端旧会话均立即失效；Redis 撤销加速，不承担唯一安全边界。若新微信关联另一份有业务历史的账号、匹配异常或归组无法验证，关闭本次操作并交正式异常路径，无自动合并。
5. 微信一次性交换在失去响应时重新取微信短码。换绑重复请求不再次迁移，响应遗失可凭新微信重新交换确认状态；通用幂等记录不保存裸 session token、挑战或手机号凭证。认证用途挑战单独隔离，不能进入业务路由。
6. 店员停用、移出、门店停用同时关闭原任职会话。恢复从新登录或明确入职处取得当前资格，旧会话不能因角色恢复重新有效。无需让同一自然人的无关顾客身份失效。会话存储、任职撤销代次和时长见 §9 与阶段 11。有效签名或缓存命中不能替代当前状态。敏感读／写获取决定当前会话和授权的可靠数据；会话依赖不可用时仅能返回暂不可用或公开数据。
7. 老板发 12 小时邀请，受邀者先微信和手机号认证，确认页只展示目标门店名称、地址与本人认证手机号，填写自身称呼并明确加入。加入以资格重验、单次消费、原 staff_id 复用或首次生成及审计原子完成。老板只有当前员工管理资格。原移出身份须走新邀请，不产生第二份员工历史。称呼只本人改。 [身份安全](https://github.com/potallllll/newpet/blob/2227fc03a698ee8f1180e04a4aa93c7c6bfe6ec1/docs/03g-customer-identity-security.md#L80) · [角色与账号](https://github.com/potallllll/newpet/blob/2227fc03a698ee8f1180e04a4aa93c7c6bfe6ec1/docs/02-roles-and-accounts.md)

### 3.2 每个请求的判定顺序

1. 校验当前端点、会话状态、可信受众与账户。校验挑战时也确认原步骤和单次有效性。
2. staff／owner 使用服务端当前的 active_staff_membership、有效 staff、有效 store。owner 还要求当前老板资格。请求体、URL 参数和前端 role 均不授予额外门店访问。老板与有效店员共享已确认日常业务权限；老板设置、员工管理、模板、邀请码和已使用赠送权益的协商充值退款保留明确授权。
3. 顾客以服务端当前 platform_user_id 查 URL 门店自己的 Customer 关系，再查原预约、订单等。首次业务且无候选冲突时，可以在同一合法动作内创建当前门店 Customer；有线下旧资料候选时按03g安全关联流程处理，冲突先返回 CUSTOMER_LINK_REQUIRED。联系方式能帮助查候选，绑定与资产归属须另验证。平台 User 在不同门店的 Customer/钱包独立。
4. 对复合资源逐层校验本店、顾客和父单，包括预约及提议、顾客及宠物、订单及明细、订单及结算范围、结算范围及退款请求、原付款及拆分、寄养及照护、钱包及原充值、SKU 及预占库存。文件上传和访问也追加用途与归属校验。
5. 在写事务内再次检查授权资格、业务状态和版本。本人规则和当前门店范围优先于幂等重放。若账号离店、旧微信已撤销或顾客资产归属未核验，历史响应不会恢复访问权。
6. OpenAPI `operationId` 标识接口，`x-access.permission_key` 标识整条接口所需的服务端权限；`x-access.conditional_permissions` 标识只有命中指定业务分支时才校验的权限。Spring Boot 从当前会话和业务事实判定分支与权限，同时校验受众、角色、当前门店及父对象。账号和设置仍使用既定角色集合。阶段 05 平台权限由独立凭证授予。 [店员端](https://github.com/potallllll/newpet/blob/2227fc03a698ee8f1180e04a4aa93c7c6bfe6ec1/docs/04-staff-miniapp.md)

老板权限常量和适用端点列于 `authorization-matrix.csv`。员工邀请和员工列表分别用 `staff_owner.invite_employee`、`staff_owner.employee_list`，全店业绩用 `staff_owner.business_statistics`。`staff_owner.record_manual_recharge_refund` 与 `staff_owner.change_order_attribution` 已按 [F-CORE-008](FIELD-REGISTRY.md) 登记为本契约的条件权限。普通充值退款和员工转出符合资格的本人订单仍按原有效员工权限办理。`GET /staff/orders` 只在传业绩归属筛选时要求 `staff_owner.business_statistics`。建立门店的 `registerOwnerStore` 按建店前资格单独鉴权。

## 4. 写事务、版本与重试

- 业务写使用幂等键。作用域由端点、动作、服务端确定的 User/Staff、门店及目标资源组成。存请求的规范化摘要，成功时同事务落原事实、审计、待投递事件、可重建结果和键。相同键且内容相同返回原结果；同键不同内容返回 409 IDEMPOTENCY_CONFLICT。相同动作换键也受已处理状态、唯一业务事实和版本保护。
- 同一事务按当前资格、店铺配置、原预约或订单、结算范围、资产及具体子对象加锁，多个同类对象按稳定 ID 排序。累计额度做当前读。不要把签名链接、第三方请求和人工操作持续时间放在业务锁内。异常回滚，已有真实外部现金交易可按原单核对或合法补记。退出、微信短码和纯读取类 POST 有各自短期语义。
- 版本字段见矩阵。预约确认/改期/开始使用 appointment_version。服务检查、开始、完成与补图使用 service_record_version。订单金额、挂单、选券、结算、补收、退款、业绩归属和寄养批次费用变化统一用 order_amount_version。退录叠加 refund_request_version，入库叠加 stock_intake_row_version。账目更新成功推进关联订单版本。服务完成/中止若同时决定可结算金额，读写订单须按同一根锁并核对影响状态。快开创建尚未存在原单时使用请求幂等键和同次有效预约匹配。
- 对明细、付款头和付款拆分的可空 customer_id，始终复制已锁定父记录的真实值。使用 NULL 安全相等验证同空或同一个合法 ID；客户端无权提交拆分归属。V001 使用非空 customer_scope_id 复合外键兜底，匿名线下商品可以整条链路为空。并发和重试校验先鉴权、再重放或走当前状态。
- `RequiredReason` 仅用于消费退款 `refund_reason`、充值退款 `wallet_change_reason` 和免单 `waiver_reason`，去首尾空白后须有文字。其他原因使用 `OptionalReason`，允许省略、`null`、空串或全空白，服务端统一归一为 SQL `NULL`，幂等比较使用同一归一化结果。适用于本人修改称呼、补图／改普通说明和寄养实际离店时间更正。有内容时去首尾空白后留存。业务检查、真实凭证和充值赠送备注按各自的提交条件校验。按业务含义检查必填的名称、联系方式及证据引用中的非空白内容。不透明凭证保留原值，按签发格式和作用域校验。
- 请求超时回原单读取已有事实后，以同键重试。遇到版本冲突重新核对服务端当前详情，同一业务更正使用新键。由于当前产品的重试窗口与错误恢复策略须随阶段 11 定稿，本稿提出候选操作语义，不固定会话、挑战、POST 重试和审计留存时长。


### 4.1 单请求数组限额

| 范围 | 契约限额 |
|---|---|
| 预约、服务开单、寄养入住／离店、宠物匹配 | 单请求最多 20 宠；照护、健康材料、商品或入库单据每批最多 20 张／项；七组洗护前后仍最多 14 张。 |
| 入住随带物品、检查标签 | 六种随带物品最多 6 项；每项检查附加标签最多 12 项。 |
| 购物车、商品条目、券发放／移除、充值赠券、券作用范围 | 单请求最多 100 行／引用；券业务类型最多 6 种；入库确认最多 200 行。 |
| 营业时间与临时休息 | 单请求最多 21 个营业时段、100 个临时休息区间。 |

以上限额用于请求体大小和单事务负载，供首轮联调验证。单次寄养照护附件限额不限制每日照护记录数；预约请求上限不限制任一时间段的顾客预约数。不改变原有各业务版本、权限和事务。

## 5. 预约、开单及服务

- 预约接口保持 wash／groom／boarding 三个业务类型。客户端可预约洗护和美容项目，护理 Other 仅门店开单。寄养使用 boarding_checkout_at 和逐宠列表。填写期望时间后只产生待确认申请；同一时间允许多笔申请。校验真实门店营业与临时关闭，不引入固定间隔、名额、抢位或支付。寄养建议容量适用原提示规则，不能当硬限制。
- 店员预约列表只读本店顾客名称和预约宠物昵称，详情按原预约同店授权返回所需联系资料、顾客 ID、宠物类型／品种和本次特殊要求 `special_request`（F-APPT-012）。顾客详情只读本人原预约的特殊要求。店员读投影与顾客 DTO 分开；三份读投影沿用相同状态和改期条件。
- 已确认预约的改期提议保留原有效承诺。双方从原预约的提议 ID 办理，任一时刻一份有效提议。服务端以原有效（或当前申请）及建议时段中较早者为准计算提前 6 小时，等于截止禁止修改。取消按未开始条件单独处理。改期、确认、到店和服务开始按同一 appointment_version 竞争。改期先赢则旧开始请求失败；同批任一宠物先开始则未接受的提议失效。正式开始发生变化时需要更新同步后的版本。
- 门店拒绝整个待确认申请以 `rejected` 终止；拒绝改期只关闭提议。未获确认的申请到原申请时段仍待确认时以 `expired` 终止。已确认预约到时保留有效承诺，店员核实未到店后才以 `cancelled` 终止并展示「已取消·未到店」。终止写入与仍开放的改期修订、审计和业务事件同事务处理。状态和取消类别的读回映射见 §9。
- 普通预约到店转服务时沿原项目、宠物及参考价快照进入待开始。原已确认预约项目后来停用，仍可按正式例外继续处理。普通预约的寄养转入需要实际入店资料和逐宠检查。预约和服务订单都只转一次。
- 临时开单可选已有或先保存本地 Customer，服务开单手机号或微信号至少一个真实资料；会员开单只选已有本店 Customer。宠物服务每宠核对真实昵称与品种，允许“不详”；商品可匿名且无宠物。快开前查同次有效预约并提示进入原单；同次对象已匹配时，新开须明确为另一次服务、用与本次匹配绑定的短期证明，经服务端复验。查预约不得跨店。
- 两入口共用项目和价格。快速服务开单完成真实的必要检查后成功提交即在服务中。一单多宠，每宠独立服务记录。洗前六项均检查，护理走原独立检查。每条发现异常或无法检查的结果须有非空说明，店员告知主人后记录真实决定。只在主人明确同意时继续。主人要求停止时，可在原未开始服务的取消动作保存真实检查和停止决定。快开未形成原单时停止提交；原同次预约仍按正常取消办理。洗美内追加护理仅添加同宠计价行，仍沿主洗美 service_record 和同一结果/进度。前后照片七组均选填，全身仅照片项。完成前真实复检。正式结束后才可结算服务费用，全部未开始且取消不构造收入。
- 取消和中止均终止原服务。重做须另开单。正常完成且符合正式未结算条件的重新处理是独立动作，原完成事实历史保留；不得借此恢复已取消或中止。补图／改普通说明不发通知，不回写金额，不触发 AI。洗护报告由顾客主动发起、已有资格核验、同订单最多一个成功报告。完整报告依赖真实广告及任务接口。 [预约](https://github.com/potallllll/newpet/blob/2227fc03a698ee8f1180e04a4aa93c7c6bfe6ec1/docs/03a-customer-appointment.md) · [店员流程](https://github.com/potallllll/newpet/blob/2227fc03a698ee8f1180e04a4aa93c7c6bfe6ec1/docs/04-staff-miniapp.md)

## 6. 寄养与分批离店

- 入住同店同客逐宠选本次日价、实际入住、预计离店、真实入住检查和已确认照护资料，日价大于零。检查为异常或无法检查时须记录非空说明及沟通后的接收决定。只有明确接收才能创建有效在住或从预约转入。原寄养预约实际不接收时，可在取消预约时保存相应宠物的拒绝检查。没有原寄养预约的到店场景只记录真实拒绝事实，不能生成在住或结算；持久化承载需在 §9 的联测门槛收口。同店同宠一笔有效在住。自带物品为选填，代喂药在特殊照护，后续真实照护按喂食／遛狗／清扫笼子／其他四类登记。F-BOARD-008 的逻辑值 `cleaning` 映射为现有 API 与 V001 的 `cage_cleaning`，界面只展示一个清扫类型，可选填一句话和照片。店员可在原记录更正日常照护，按原版本留痕。顾客过滤门店内部事件及附件。
- POST boarding-checkouts 对实际接走的宠物创建本批 settlement_id，记录本次确认应收和离店事实。锁原单、本批及逐宠记录；入住 ≤ 实际离店 ≤ 服务器当前。逐宠数满足入住 < 北京时间当日 03:00 ≤ 实际离店的截点，按本次日价乘以晚数。不跨截点为零晚，入住恰在 03:00 不计该晚，离店恰在 03:00 计入。其他宠物仍在住；已离店未付显示待结算，后续走原批收款、免单或挂单。
- PATCH boarding-times 只处理归属此批且财务未结算的原明细。修正的实际时间可晚于首次费用确认，前提是未超过本次服务端时间。重新核对并原子重算晚数、基础费和本批应收，入参仍须带原单金额版本及逐宠版本，接受选填 `audit_reason` 并保存原实际时间、原晚数、金额和操作者。首次 `boarding_checkout_confirmed_at` 保留。日价更正在首次费用确认前，确认后未收款可依原规则调最终应收。已收或免单按原单补收/退款，时间和账目事实保持可追溯。
- 挂单标志、挂单时间、解除时间分开。手动解除与收款成功解除均算已解除，查询保留原挂单时间。真实服务在住／离店、顾客展示、挂单和财务状态来自各自事实。寄养加餐是同店同顾客且有效寄养关联的普通商品，线下交付不增加领取凭证或确认投喂流程，必要时照护独立记录。 [寄养规则](https://github.com/potallllll/newpet/blob/2227fc03a698ee8f1180e04a4aa93c7c6bfe6ec1/docs/04-staff-miniapp.md#L1660)

## 7. 收退款、钱包、券与商品

| 操作 | 服务端提交条件及结果 |
|---|---|
| 结算范围 | 普通消费单使用一份整单结算。既有条件满足时由服务端创建或复用排序明确的结算范围，端上无需额外订立一个结算对象。寄养各批独立初始结算；原单只汇总实际确认的批次。 |
| 选券及调价 | 顾客和门店资格、范围、有效期、当前锁及规则快照全部由服务端核验。每张券只占一单，普通券每单最多一张（含多个寄养批次）。同事务先核对移除旧锁再取新锁，失败恢复原合法锁。选券重新产生报价/版本，若此前有人工最终报价，重新核对，不能把旧券优惠从同一已折价金额再扣一次。锁不延长有效期。 |
| R09-01 | F-ORD-013 = F-ORD-014 - F-ORD-010。接口只读该差额，写入仅可在待结算按权限改最终应收。V001 由生成列计算。券与活动的优惠净影响只计一次。核销明细和规则留在 coupon_redemption.calculation_snapshot，历史退役优惠字段不进入新 DTO 写入。 |
| 记录实际收款 | 原服务完成或合法结束且费用明确，商品依库存/成交规则，寄养依确认离店批次。请求必传页面当前看到的 `PaymentConfirm.final_receivable_amount` 作为断言。服务端在事务内核对版本及锁定应收，金额不一致返回 `409 RECEIVABLE_AMOUNT_CONFLICT`，应收仅能从原待结算调价接口修改。应收断言通过后，最多两种不同支付方式且拆分金额之和须等于锁定应收，金额合计不符按 `422 PAYMENT_TOTAL_MISMATCH`。钱包按先本金再赠送扣减，线下渠道按实际收款记账。失败时不创建付款、扣钱包、核销券或更新库存。 |
| 免单与补收 | 明确确认应收为零且有原因才免单，无虚假付款或钱包流水，适用商品正常出库，券成功后自动核销。结清后金额及首笔拆分锁定，少收且有可核实依据才在同一原结算追加补收。补收包含外部渠道时必须提供真实 `payment_occurred_at`，仅使用钱包时取实际扣款入账时间。首结、补收和超时商品补记都最多使用两个不同渠道，同一渠道即使金额不同也只能有一条拆分。线下一次合并付款分开按各原单记录，证据范围内份额总和不得超实际款项，禁止混合收银台。 |
| 消费退款 | 保存原退款录入版本不记账。确认时必填 `refund_reason` 和 `refunded_at`，后者使用带时区的 RFC3339 记录实际退款发生时间，另记服务端入账及审计时间。只退原实收且未退额度，分配到原付款渠道及原拆分，线下原路由门店核实。钱包只恢复原组成，先剩余本金后赠送。退款无需额外审批。退款与实际退货分别记录，只有实际收回且可再次销售数量才回库。 |
| 充值 | 本店按原钱包登记真实充值。本人顾客可查看本店余额总额、本金、赠送余额、可用券和钱包流水。首次没有钱包时，店员查询返回零余额和空 row_version；提交首次充值带空版本，由服务端锁该 Customer 后创建并登记，其他并发重查当前版本。赠送余额大于零或至少选一张赠券时，wallet_note 去空白后必填。原充值、到账、流水和赠券同事务。 |
| 充值退款 | `RechargeRefundInput` 必传 `refund_mode`、`wallet_change_reason` 及真实发生时间 `occurred_at`。同事务锁定原充值、钱包和关联赠送权益，查原赠送金消费和赠券核销历史。按下表检查模式及权限。任何成功退款均校验原充值剩余实收、本金可扣余额和实际退还金额，追加流水及自动审计。 |
| 券与活动 | 顾客本人可领本店 72 小时一次码，获得一个内容；成功后按北京时间一个日历月有效，月末取月末。门店可发券或移除未用、未锁定实例。结算成功才自动核销，已用券不由门店复活或退款退回。模板维护可选填 `coupon_note`，仅授权模板读视图展示。满减模板须填正数门槛与抵扣额，金额抵扣须填正数抵扣额，折扣比例严格大于 0 且小于 1，可选正数优惠上限。模板修改保留已发快照，既有实例按原授权读回。券模板读入口统一为 `GET /staff/coupon-templates`，省略 `template_state` 或传 `active` 只返回本店启用且可发放的模板，`disabled`、`all` 仅本店老板可查。普通员工请求这两项返回 403；分页游标按门店、调用者权限及筛选隔离。 |
| 商品和库存 | 需求提交不占库存，店员确认时指定本店有效业绩归属并逐行预占。默认 24 小时按门店既有配置。有效期任务和记账在同订单版本竞争；取消/超时只释放对应预占，成交后仅一次出库。超时已真实收款且交货，核实后关联原需求补记。分别记录成交、交货、实际收款和补记时间。外部渠道用已核实的收款引用恢复实际时间，也可传 `payment_occurred_at` 并核对真实凭证。传两者时须相符；不同外部渠道发生时间不同须逐分项引用原证据。保留历史，普通成交没有新增线上交付字段。 |
| 提取和入库 | 手录与 AI 图片走同一原入库表单，后者只把识别结果填回，真实生效只在点击确认后。已有 SKU 关联，新品补齐后与本次一并提交。现阶段无付费校验。识别重复图片只提示，确认幂等仍生效；纠错从库存管理写调整，保留原入库事实和库存预占。 |

| `refund_mode` | 办理条件与服务端结果 |
|---|---|
| `standard` | 本店老板或有效员工可办。关联赠送金和赠券均未用时沿普通退款规则，全额退款按原规则回收尚未使用的关联赠送权益。任何一项曾用过均返回 `409 RECHARGE_REFUND_OWNER_MANUAL_REQUIRED`，老板和店员收到同一结果。拒绝后原账本、权益和版本不变，需由老板另行明确提交手动退款。 |
| `owner_manual` | 仅本店老板办理，且原充值关联赠送权益至少一项曾用过。店员提交返回 `403 OWNER_REQUIRED_FOR_RECHARGE_REFUND`；老板提交但赠送权益均未用返回 `422 RECHARGE_REFUND_MODE_INELIGIBLE`。成功时只记录协商后的实际退还本金，自动折算及自动回收赠送权益均关闭。 |

库存调整统一调用 `POST /staff/products/{sku_id}/inventory-adjustments`，路径标识使用商品唯一 SKU 的 ID。删除 SKU 保留 `If-Match` 版本断言。删除商品分类时保护本店兜底「其他」，在同一事务按稳定顺序锁分类和兜底，将其商品迁到本店「其他」后再删除原分类。创建／编辑商品分类关联使用同一锁约定，加锁后重查分类仍有效。

## 8. 通知、私有媒体与故障

- 只有普通、重要两档。预约、服务、结算的已确认事件按原模块生成站内通知。普通服务补图和中止不通知。查询、重复提交、仍待处理或旧版本重放不新增通知。工作台按四类原业务状态投影，预约确认覆盖所有仍有效待处理承诺；其余当天事项与历史、跨天挂单查询各走原规则。
- 发布通知时仅向当前有权收件人保留最小摘要与业务跳转信息，跳转接口再验本人、本店和父对象。微信通知仅在客户授权和平台能力就绪时尝试；短信暂未开放。站内消息和短信状态分别处理。
- 私有媒体采用发起、上传、校验、授权下载四步。上传凭证仅对应目标归属、用途、限制及短期对象，成功前不允许附加给业务对象。签发下载前重新校验业务可见性。门头与营业执照只收 JPEG／PNG，分别不超过 3,145,728 字节和 10,485,760 字节，实际解码核对类型和大小，门头另验 1:1。营业执照仅老板或获授权入驻流程按原规则读取。本批建店用途只支持首次入驻，既有门店资料变更见 §9。顾客端中止服务仅展示中止状态，本次过程说明、结果版本、媒体及缩略图均隐藏。媒体下载亦重验可见性，门店内部合法记录及其他已获授权历史继续按原规则读取。原仓库的证照公开边界继续适用。
- 占位 AppID 不返回真实微信身份。Redis 未命中走权威读，丢锁不使库存或券可以重复确认。依赖故障下公开门店/商品可按允许的数据降级，私有业务保留访问判定。跨店提醒未接通、安全校验不可用时按原不可用提示及允许继续规则处理，不能显示“未查到风险”冒充已查询。相关审核/授权查询单独按 03h、04§6.5 上线。

预约查询先读取 V001 的原预约基础状态与原有效承诺，再读取同店、同顾客、同预约的 `appointment_revision`。仅当基础状态为 `pending` 或 `confirmed` 且 `change` 修订仍为 `pending`、服务端时间未达截止且当前业务仍允许处理时返回 `active_proposal`。初始申请修订、已关闭或已失效的修订不参与派生。到期由权威读和写事务按服务端时间判定，后台任务尚未执行时也不能用旧提议确认；未确认超时按 `expired` 对外返回，并由状态转换事务落库。

| V001 基础状态或业务动作 | `AppointmentSummary.appointment_status` | 展示及读回 |
|---|---|---|
| `pending` / `confirmed`，无有效改期 | 同 V001 | 待门店确认 / 已确认，`active_proposal=null`。 |
| `pending` / `confirmed`，有门店提出的有效改期 | `awaiting_customer` | 待顾客确认新时间，提议与原承诺分别返回。 |
| `pending` / `confirmed`，有顾客提出的有效改期 | `awaiting_store` | 待门店确认新时间，提议与原承诺分别返回。 |
| 门店拒绝整个待确认申请 | `rejected` | V001 写 `rejected`。顾客显示「已取消」，有真实填写的门店原因才展示。 |
| 原申请到时仍未获确认 | `expired` | V001 写 `expired`。顾客显示「已取消·确认超时」。 |

`awaiting_customer` 和 `awaiting_store` 只存在于 API。改期被拒绝、撤回或失效时恢复展示原基础状态；终态始终返回 `active_proposal=null`。取消类别只投影登记的业务结果，审计原件与内部备注保留在服务端。

## 10. 首批联调顺序与证据

1. **入口资格**。两端身份、本人和本店权限、旧会话撤销、切门店及字段隔离。测试环境可用显式合成身份测试控制器契约；真实微信登录、手机号认证和换绑另在有效测试号验证。
2. **首条可走通链路**。顾客创建预约、门店确认、到店转单、开始/完成、柜台记账、本人回看。验证 6 小时边界、同次预约重复开单、终止后再开和新旧状态竞态。为一人门店保持一次明确确认即可完成动作。
3. **原班次内分批离店及原单账本**。甲批先离店挂单、乙批仍在住，两次确认不同结算范围，查结清后的挂单。验零晚及入／离店等于 03:00，实际更正、收款抢占、退款原路及同款多单分摊。
4. **商品及储值闭环**。同款库存竞争、超时释放与结算、选券、赠券充值和原充值退款。用一个关联的对外账单验证原始应收、总差额、最终应收、实收、退款和净消费，去重后按正式日期记账。
5. **有依赖功能和开放批次**。入库拍照、私有图片、AI、邀请码、微信通知以及平台后续按各门槛完成。真机验收以实际微信能力为证据，数据库空库探针继续作为独立记录。阶段 08 契约评审完成也需遵循 DEC-EXEC-01/02、阶段 11/12 与开工授权。
