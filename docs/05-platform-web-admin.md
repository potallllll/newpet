## 1. 目的与使用者

平台人员用网页端审核门店资料、处理风险和争议、承接门店无法自行办理的事项。老板和店员通过小程序处理本店预约、服务、收款、商品与库存。平台操作尽量沿原申请、原案或原单完成，并将受理结果回写给有权查看的门店或顾客。

| 工作场景 | 要解决的问题 | 期望结果 |
|---|---|---|
| 审核与风险处理 | 在不同记录和消息中找材料，容易遗漏截止或核错版本。 | 从待办进入原申请或原案，把材料、有效版本、期限和允许操作放在同一处。 |
| 客服核实 | 线下交易已经发生，客服需要通过原单核对事实、权限和处理记录。 | 可以查原单、登记材料并让门店查结果。符合严格条件时沿原有补收／退款代办。 |
| 运营与履约 | 广告、平台积分实物与 AI 顾问权益随不同功能开放。 | 从对应列表处理，在原记录追溯变更与经办人。 |

这些是工作场景。所有有效平台管理账号使用同一系统角色和同一权限集合。

验收以可观察结果为准。已开放功能的待办计数和筛选列表一致；一次合法状态转换只生效一次；无权或已失效会话请求拒绝；原案与双端展示可追溯同一个版本。上线后可统计待处理数量、审核耗时与退回原因，运营时效目标待实际人力与业务量确认。

## 2. 登录和账号

> platform_web_login: username_password
> platform_admin_role: platform_super_admin
> platform_admin_permission_model: uniform
> multiple_platform_admin_accounts: true

- 使用独立的账号密码页面。可配置多个独立平台管理账号，登录成功后进入同一后台。每笔操作以实际登录账号留痕。
- 当前平台 Web 只有 02 中的 Platform Super Admin。所有有效平台账号权限一致，统一配置，不制作客服、审核、运营独立角色或逐人勾选权限。顾客、Merchant Owner 和 Staff 的小程序登录及任职仍按原规则；小程序身份不能访问平台入口或接口。
- 未登录先进入登录页，校验失败不建立会话。账号停用、退出或会话失效后拒绝继续访问；涉及写入时服务端逐次校验会话、原对象、当前状态与版本。登录态和密码处理的技术契约见后续阶段08／11；首个账号如何发放、密码重置流程与会话策略仍待设计。
- 统一权限适用于相同功能和相同对象条件。业务状态、功能是否开放、代办条件与原记录保护均继续生效。权限标识是服务端校验和验收依据，仍按下表映射。

## 3. 首页与左侧菜单

首页顶区显示已启用模块的待办数字卡，首批用门店资料待审、待核实账号／门店异常、待处理原单异常；对应功能启用后再加争议待审、食品待处理、顾客风险待审与待发货。计数按去重后的当前可办理记录生成，点击进入同条件列表；读取失败显示重试，不能用 0 代替失败。首页只用它来开始工作，原单详情显示业务历史。

左栏固定三组九项，组内按下列顺序。未开放的模块不产生可执行入口。操作日志设一个统一查询入口，页面详情也可查看该记录的有权审计摘要。

| 菜单分组 | 二级模块 |
|---|---|
| 商户与账号治理 | 1. 门店管理与资料审核；2. 门店与账号异常；3. 门店停用收尾 |
| 争议、风险与客服 | 4. 消费争议与裁决；5. 食品风险与厂家回应；6. 顾客风险与授权审核；7. 原单异常与客服核实 |
| 平台运营与审计 | 8. 积分实物与总仓履约；9. 广告与 AI 权益 |

## 4. 页面与操作

列表共有原单号／原案号跳转、分页、加载、无结果、失败、越权和版本已变化的状态。短记录可用详情抽屉，需核对多份材料或并排比较时使用详情页。返回列表保留筛选与位置。下列标签为页面筛选，直接映射正式业务记录。缺少契约的技术状态先登记。

| 页面 | 搜索、列表与分组 | 详情、动作及结果 |
|---|---|---|
| **1. 门店管理与资料审核** | 按门店名称／编号、申请日期、审核结果查找。列为门店、申请人、提交时间、变更项、状态；待审核／历史。 | 并排展示当前有效资料与本次提交的门头、名称、地址和营业执照。查看受限证照、批准或退回。退回记录原因，门店继续显示原有效版本；批准后发布新版本及结果。门店仍可按02自助注册，无首次开通人工审核。按[04 §3.0.6](04-staff-miniapp.md)处理单份待审、撤回竞态及生效后168小时。 |
| **2. 门店与账号异常** | 按账号或门店标识、异常类型、时间、是否已核实筛选。列为门店、问题类型、关联原账号、发生时间、处理结果。 | 查看绑定和任职事实、登记核验材料和处理结果；账号绑定异常未核实前维持原冲突阻断。恢复身份的证据、写入动作和接口待契约确认。原身份和历史按[03g](03g-customer-identity-security.md)保留。 |
| **3. 门店停用收尾** | 按门店或主要遗留业务查询。列表显示门店状态、在住、未结算、预占、争议、上门喂养及待领实物数量。 | 停用前提示影响，停用后逐项跳原记录、登记去向和结果。上门喂养按[03j](03j-customer-home-feeding-marketplace.md)接续；领取门店按[03k](03k-customer-loyalty-points.md)处理。其他业务只能按已确认动作收尾，保留在住、账本和历史原归属。 |
| **4. 消费争议与裁决** | 按案号、门店、提交日期、回应／补证阶段及当前裁决查找。列为案号、门店、状态、真实截止、处理结果。 | 查看原投诉、回应、补证和有权读取的原件；预览脱敏副本、人工评证等级、按事实点裁决、独立确认已解决。7天回应和3天补证沿[03h](03h-customer-risk-feedback.md)，各端只读获准展示的结果。 |
| **5. 食品风险与厂家回应** | 按案号、标准品牌、批次、关联门店及厂家回应状态查询。列为案号、品牌／批次、反馈热度、厂家回应、门店知悉；未识别品牌有次级入口。 | 查看原案、按原案联系厂家、录入并审核回信、查询门店知悉。厂家回应由平台处理，门店继续仅知悉。热度、集中反馈与归属按[03h](03h-customer-risk-feedback.md)、[03f](03f-customer-messages.md)。品牌归一见§5。 |
| **6. 顾客风险与授权审核** | 按记录号、提交门店、审核状态、提交日期及授权冲突查找。列为记录号、对象分类、来源、状态、时间。 | 查看有权限的提交内容和证据，审核通过或退回，核实授权变更及认证手机号冲突。审核通过仍按原共享授权、可见期及查询限频校验，顾客端不返回风险记录。 |
| **7. 原单异常与客服核实** | 按原单号、门店、业务类型、异常类型、时间查找；列原单、门店、问题、核实状态和结果。 | 按原单查账、登记客服材料、核实24小时超时关联补记的库存冲突、处理食品风险／奖励自提内部备注误填、跟进停用店遗留单。代办按§6。 |
| **8. 积分实物与总仓履约** | 随积分实物功能开放。按兑换单、领取店、奖励及状态筛选；列兑换单、奖励、领取门店、发货／领取状态。 | 管理平台奖励及库存、在原兑换单确认总仓发货、核实错发／未收到等。停用自动退分与720小时系统默认已领取分别显示，人工补发和积分处置范围仍按03k待定。 |
| **9. 广告与 AI 权益** | 随对应模块开放。按配置或门店、资源类型、状态查找，展示启停、适用门店及已登记的权益状态。 | 沿03o／03p配置启动封面及首页底部广告；沿03l查看或管理已确认的 AI 顾问门店权益，保留配置变更。 |

## 5. 食品标准品牌归一

入口放在「食品风险与厂家回应 → 待识别品牌」。所有有效平台管理账号按统一权限处理。列表显示原始文本、关联对象摘要、待识别状态，支持按原文字、标准品牌和状态筛选。详情可对照已有标准品牌及别名，确认绑定稳定的标准品牌 ID 或保留待识别。保留原始输入、映射前后值、经办账号和时间；无法可靠确认时维持待识别，顾客继续看到原提示。映射按[03b](03b-customer-pet-profile.md)和[03h](03h-customer-risk-feedback.md)进入正式品牌匹配，不能凭同名强绑、改写历史投诉或自动补发旧消息。新增标准品牌、别名冲突与误识别撤销的接口在字段和权限阶段登记。

## 6. 原单异常处理与代办

平台从原单查账、登记客服材料与处理结果。门店可从原业务详情查看有权结果。商品补记遇库存冲突保留原单和真实证据，按[03e §13.1](03e-customer-products.md)核实；食品风险和奖励自提备注误填仍由平台按各业务记录处理。

正常可自助时引导老板或有效员工走原单追加补收／消费退款。**只有门店账号已停用或系统确实锁死、该门店无法自助时**，才向有效平台管理账号开放原单的代办动作。复用同一套补收／消费退款，核对凭证、真实发生时间、退款原因、渠道及额度。仅有数字错录且缺少真实资金事实时记录材料和核实结果，不产生假流水。代办和查询权限分别校验；具体规则以[03d §11.3](03d-customer-orders.md)为准。

## 7. 操作权限映射与留痕

| 已有权限标识 | 网页动作 | 校验要点 |
|---|---|---|
| `evidence.review` | 消费争议 → 审核第三方佐证、人工标证据等级 | 高／中／低是证据等级。已审原件和公开脱敏副本按来源权限读取。 |
| `complaint_review.decide` | 消费争议 → 作出事实裁决 | 按事实点记录判断、理由和证据。 |
| `complaint_review.resolve` | 消费争议 → 确认已解决 | 独立读取解决状态，不能用裁决代替确认。 |
| `customer_risk.review` | 顾客风险 → 审核通过／退回 | 审核和授权分别校验，成功后仍按跨店范围返回。 |
| `reward_fulfillment.manage` | 积分实物 → 创建／更新发货任务、确认发货 | 沿原兑换单；权限本身不授予人工取消、退积分或补发。 |

门店资料审核、客服资料查阅、品牌归一、日志查询与受限资金代办分别是独立动作。已确认能做的动作统一授予有效平台管理账号；未登记的权限标识、附件鉴权、账号与会话接口及结果回写在阶段08／09／11落实。列表、详情、下载、附件和直接请求执行同一授权判定。日志保留实际账号、服务端时间、对象、处理前后及结果；日志统一入口只读。

## 8. 发布分批与范围

- **小程序首批上线依赖**：账号密码登录、待办首页、门店资料审核、账号异常受理、门店停用影响核对、原单异常受理与已确认的代办入口。消费争议、食品风险及顾客风险各自随小程序功能开放配套处理和结果回写；品牌归一随食品风险开放。缺少有权人员、可用处理入口或回写时，相应功能延后开放。此处约定上线依赖，正式开发仍按项目阶段准入。
- **随模块开放**：积分总仓及实物异常、广告和 AI 权益。完整平台后台、批量运营、报表和外部旧系统导入留后续阶段。
- **本期范围**：门店日常预约、洗美、寄养、收银、入库和老板设置继续用店员小程序。平台 Web 保持审核、风险、运营与异常处置。门店 Web 收银台、进销存后台、分销、外部团购和跨业务混结不进入首期。

## 9. 第一轮评审与验收

1. 两个有效平台账号用各自账号密码登录，可见相同菜单和操作能力；各自操作日志可区分，停用／过期会话直接请求拒绝。
2. 门店撤回资料修改申请与平台审批同时发生，只有先成功的状态转换生效；旧版本和重试不会覆盖当前版本，批准后双端读取同一份生效资料。
3. 老板失去原号码且已有在住宠物，客服核验能按原账号定位，处置后可追溯，既有资金和历史保持原关联。
4. 门店停用时同时有在住宠物、欠款、未发奖励、已接单上门喂养，停用界面能逐项查看原业务并显示真实收尾结果。
5. 验证第三方证据等级、事实裁决、确认已解决、食品回信与风险撤权各按原动作生效，双端可见范围正确。
6. 实收100元仅记80元且凭证可核实时，店员在原单走补登漏记的20元，顾客不重复付款。门店仍可自助时平台代办拒绝；停用或系统锁死有权代办时，重复提交只确认一次。
7. 商品需求超时且已真实交货，能核实且库存满足时按原需求关联补记一次；库存冲突时只登记核实状态，不恢复旧需求或写入半笔流水。
8. 品牌不能可靠匹配时保留待识别；可靠匹配后用正式标准品牌 ID 参与后续匹配，保留原文字、版本和经办审计。首页待办卡和点击后的列表数量一致。
