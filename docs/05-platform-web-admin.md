## 1. 目的、对象与三端职责

NewPet 服务老板单人经营或全店 2～3 人的社区宠物店。老板和顾客通常熟悉，线下确认项目、交付和交易，预约与服务状态及时记录，财务可在下班后按原单登记。平台 Web 帮门店承接审核、争议风险、按门店导出及店员端无法自助的异常。

**客户端与店员端核心业务正常运行，是平台 Web 接入的前提。** 一人值店时可在小程序完成预约确认、洗美、寄养离店结算及商品成交，顾客通过客户端看到对应结果。Web 接入已通过验收的原业务和原记录，具体发布顺序见 §8。

| 场景 | 客户端 | 店员端 | 平台 Web |
|---|---|---|---|
| 预约、洗美、寄养与货品 | 提交预约／商品需求，查看本人服务、寄养动态及账单 | 原入口办理预约、两种快捷开单、寄养入住、离店结算和商品处理 | 编号查原记录；满足 §6 条件时直接补漏单、修改允许项或删除错误单 |
| 熟客线下收退款 | 查实际记账结果 | 逐张原单登记实收份额；普通差错沿原单补收／退款 | 查账与客服核实；在受限条件下沿原单代办 |
| 门店资料 | 读取已生效且可公开的门店资料 | 老板提交、撤回待审申请并查看结果 | 对比快照、审查、生效 |
| 消费争议、食品与顾客风险 | 「我的 → 投诉与建议」提交；读取获准公开内容及本人消息 | 本店回应门店争议、登记食品知悉、提交顾客风险 | 审核和最终裁决、联系厂家、核验顾客风险及共享授权 |
| 平台积分实物与权益 | 查本人兑换与顾问／广告可用状态 | 实际交付后登记领取；有效权益内由老板设置本店启用 | 总仓发货、处理原兑换异常、管理平台配置 |

页面取舍参考《板栗狗门店后台合并.md》§2.2、§2.4、§2.5、§2.7～2.8。待办数字卡直达筛选列表，导出先核对范围，订单详情同屏呈现金额、明细与办理时间轴。三端的业务规则沿 NewPet 的[客户端](03-customer-miniapp.md)、[页面蓝图](03i-customer-screen-blueprint.md)与[店员端](04-staff-miniapp.md)。店员端布局按[10d](10d-staff-layout-and-owner-menu-checklist.md)。

Gemini V2.0 对本版的补充落在停用影响清单、库存三数和导出记录三个页面场景，分别见 §4.3、§4.7 和 §5.2。

- 登录页显示账号、密码和「登录」。提交时禁用重复点击，失败显示通用认证错误，可重试。凭据校验成功后进入首页。密码、凭证及会话信息不得出现在列表、日志或导出。

- 服务端按当前会话、操作权限、对象归属、动作条件和状态逐次校验；写入额外复核业务版本。账号发放、密码重置及会话参数在阶段 08／11 收口。

## 3. 首页、菜单与通用交互

### 3.1 首页待办

卡片显示名称、当前实际可办记录数、「查看待办」。点击后带入同一门店范围与筛选，卡片和列表用同一计数口径，各原记录或审核项按该行指定粒度去重。平台待办允许任一有效平台账号处理；查看页面不锁定记录。成功办理刷新计数，真实零显示 0，查询失败显示「重试」。首页只放待办。

| 批次 | 数字卡 | 跳转列表及口径 |
|---|---|---|
| Web 首批 | 门店资料待审 | 模块 1 → 资料待审核，按原修改申请 |
| Web 首批 | 待核实账号／门店异常 | 模块 2 → 待核实，按原异常记录或审核项 |
| Web 首批 | 待处理原单异常 | 模块 7 → 待核实／可办理，按原异常关联，包含有待处理的补单请求 |
| 随消费争议 | 争议待审 | 模块 4 → 待平台处理，按案去重，包含可处理的内容、材料或裁决 |
| 随食品风险 | 食品待处理 | 模块 5 → 待联系厂家／回信待审核，按原案去重，等厂家回信仅在列表反映实际状态 |
| 随顾客风险 | 顾客风险待审 | 模块 6 → 风险提交待审核，按原审核项 |
| 随积分实物 | 待发货 | 模块 8 → 待总仓发货，按未结束原兑换单 |

### 3.2 左侧菜单

| 一级分组 | 二级模块及顺序 |
|---|---|
| 商户与账号治理 | 1. 门店管理与资料审核 → 2. 门店与账号异常 → 3. 门店停用收尾 |
| 争议、风险与客服 | 4. 消费争议与裁决 → 5. 食品风险与厂家回应 → 6. 顾客风险与授权审核 → 7. 原单异常与客服核实 |
| 平台运营与审计 | 8. 积分实物与总仓履约 → 9. 广告与 AI 权益 |

页头提供「首页」、当前平台账号、「退出登录」和统一只读「操作日志」（§7）。板块未开放时没有可执行入口。导出在模块 1，异常改数／补单／删错单在模块 7，「待识别品牌」在模块 5。

### 3.3 列表、详情与弹窗

- 筛选条上方显示页面及当前门店范围。查询、重置、分页统一，切换筛选回到第一页，返回列表保留筛选、页码和滚动位置。列表默认按相应提交／记录时间倒序；待办页以当前可办状态优先。显示时间注明时区，日期筛选依该字段的业务时间。
- 列表状态包含加载、初始为空、筛选无结果、读取失败、无权、登录失效。详情区分脱敏内容、原件、历史和当前有效值。需要对照资料或核对多笔流水时用详情页，轻量查阅用抽屉。
- 状态用文字与颜色共同表达。筛选、列表行操作和弹窗支持键盘，关闭弹窗时焦点回到触发控件。窄窗口允许表格横向滚动，门店和原单号始终可定位。
- 写动作的弹窗显示门店、编号、当前状态、拟写内容和影响。一次明确确认后提交；提交中禁重复，结果未知先查同次请求结果。版本变化提示刷新并重新核对，无权或资格变化不写入。失败保留可重试的输入，成功后以服务端结果更新列表、详情及计数。列表状态、页签和筛选标签映射实际业务字段。

## 4. 九个模块页面规格

### 4.1 门店管理与资料审核

- **入口、筛选**　「门店」按名称／编号、门店状态查询。「资料申请」按门店、提交日期及审核状态查询，分待审核与历史。
- **列、状态**　门店编号、名称、门店状态、资料版本；申请列为申请号、门店、申请人、提交时间、变更项、审核结果。结果为待审核／已通过并生效／拒绝／已撤回。
- **详情**　并排展示现行四项与本次完整快照，标出门头、名称、地址、营业执照的差异。执照仅本店老板及平台有权人员读取。门头与执照沿各自上传规格。
- **弹窗与结果**　「通过并生效」确认本次完整快照，原子更新对应有效版本；「拒绝申请」录入审核意见供老板查看，原有效版本继续展示。撤回或版本冲突时刷新结果。门店只保留一份待审，撤回／生效先成功者生效，生效满 168 小时方可再次提交。首次注册按本店自助建店。见 [02](02-roles-and-accounts.md) 与 [04 §3.0.6](04-staff-miniapp.md)。
- **按门店导出**　在门店详情用「导出本店数据」，查看该次生成状态及下载结果，详见 §5.2。

### 4.2 门店与账号异常

- **筛选**　门店编号、原账号编号、异常类型、发生日期、是否已核实。手机号冲突从对应审核项跳转，定位服务端认证身份。
- **列、状态**　门店、原账号摘要、异常类型、发生时间、待核实／已登记结果、最近处理时间。
- **详情**　显示原绑定和任职事实、相关材料与处理历史；未核实或不能唯一匹配时维持原冲突阻断。门店接续营业且有在住或未结算时，可跳对应原业务。
- **弹窗与结果**　「登记核实结果」显示原主体，记录事实、凭据引用、处理摘要；保留原身份和历史。解除冲突、恢复访问如需写入，须用 [03g](03g-customer-identity-security.md) 的核验口径及阶段 08／09／11 登记的动作。平台人员账号生命周期按 §2。

### 4.3 门店停用收尾

- **筛选**　门店名称／编号、当前账号状态、遗留业务类型。
- **列、状态**　门店、账号状态及下列六项影响的实际数量。点击任一项进入该店对应原列表，进详情可追到原记录。
- **详情与弹窗**　「查看停用影响」显示清单和取数时间。读取失败的项目显示「暂无法核对」并可重试，真实无记录显示 0。「确认停用」展示影响和结果去向，提交时按门店状态治理契约重验当前状态及版本。成功后进「停用收尾」查实际结果。需要留存表格时可跳同店导出，复用 §5.2 的范围和权限。
- **结果**　上门喂养按 [03j](03j-customer-home-feeding-marketplace.md) 由系统接续，保留原接单人与历史，当前接续店重新确认后才具备对应联系资料资格。积分实物按 [03k](03k-customer-loyalty-points.md) 处理原兑换。其他事项从原预约、原订单、原投诉进详情，平台直接修复的范围见 §6。临时休息沿门店营业设置。

| 停用影响 | 清单要显示的记录 |
|---|---|
| 在住寄养 | 在住宠物数，进入原寄养单查看状态 |
| 未结算／挂单 | 未结算单数及可核实的待收金额，进入原单查看应收、实收和退款 |
| 有效商品预占 | 仍持有预占的订单数，进入原订单查看 SKU 与预占 |
| 未处理消费争议 | 待回应或待平台处理的投诉数，进入原案查看阶段与截止 |
| 未结束上门喂养 | 原需求与现任负责店，显示按原规则接续的结果或无候选提示 |
| 未完成领取 | 原兑换单及履约状态，显示按原规则取消、退积分和重要通知的结果 |

### 4.4 消费争议与裁决

- **筛选**　案号、对象／门店、提交日期、内容审核、回应／补证、事实结论、是否已解决。默认可切「待平台处理／全部」；同一原投诉可显示多项独立状态。
- **列、状态**　案号、对象与入驻标记、提交时间、审核／回应阶段、真实截止、事实结论、解决状态。详情顶部突出 **7 天正式回应**、真实截止和剩余；首个回应后突出 **3 天补证**，保留原逾期历史。未入驻门店标记「未入驻」，入驻并认领后按原案仍可回应条件办理。
- **详情**　原投诉、店员端正式回应、补证／处理情况、第三方材料、相关原订单以及公开版本。原件按对象授权，公开预览只读取脱敏副本。页签「建议」给平台查询客户端建议原文和时间，门店无回应待办。
- **弹窗与结果**　「内容审核」预览公开副本，支持审核通过、退回修改或拒绝；通过后按规则公开。「审核佐证」逐条记录人工高／中／低等级及审核结果。「作出事实裁决」记录各事实点、证据、理由和结论；逾期仅表达未回应。「确认已解决」独立确认，仅回写解决状态。需要额外材料时在原案记录单独要求和截止，原 3 天窗口按原期限显示。状态、通知、公开顺序和期限见 [03h §4～7、§12.1](03h-customer-risk-feedback.md)。异议由客服承接。
- **跨模块**　食品原案的共同内容审核、证据与裁决复用此详情；厂家事实在模块 5 办理。批量审核按 [03h §9](03h-customer-risk-feedback.md) 后续接入稳定审核项、版本、预检及逐行结果。

### 4.5 食品风险与厂家回应

- **筛选**　案号、标准品牌／待识别、批次、明确关联门店、联系／厂家回信状态、热度和日期。
- **列、状态**　案号、品牌／批次、低／中／高热度及更新时间、厂家联系与回信审核状态、关联门店知悉状态。本案与门店的「已知悉」分别显示。
- **详情**　食品原案、同批有效反馈、真实联系历史、厂家原回信与审核稿、门店知悉轮次。食品集中反馈触发及续期和热度按 [03h §8](03h-customer-risk-feedback.md)，页面读服务端结果。
- **弹窗与结果**　「登记联系厂家」记录真实联系；「录入回信」保存来源、内容与收到时间；「审核厂家回信」校对身份、材料和可公开内容，通过即记厂家回应，未回信显示「平台核查中」，无厂家回应期限。平台直接联系厂家。门店只在其关联提醒上明确知悉；确需重新知悉的，平台按 [03f §13.3](03f-customer-messages.md)在原提醒明确发起，普通更新或重发无需开新轮。仅另有明确门店销售／处理争议时，该门店部分的正式回应按原争议规则。
- **次级入口**　「待识别品牌」见 §5.1。内部备注误填从同一提醒跳模块 7 留痕处理。

### 4.6 顾客风险与授权审核

- **筛选**　事件／审核项编号、来源门店、顾客相关／宠物相关、提交时间、审核状态及身份冲突。
- **列、状态**　记录号、对象类别、来源、真实发生／提交时间、待审核／通过／驳回／撤回和实际可共享状态。审核结论与授权有效性分列。
- **详情**　查看提交内容、关联原业务、客观经过、证据和授权。审核前只供提交店有权人员和平台；审核后展示资格由真实业务触发、双方门店授权、顾客分项同意、认证手机号唯一匹配、同店同顾客每自然月 3 次上限及 12 个月可见期共同决定。顾客端始终不展示已审或未审风险记录。
- **弹窗与结果**　「审核通过／驳回」记录实际结果，驳回意见回到提交人。审核前原提交人可撤回；核验顾客来电的授权变更按对应分项和当前授权生效，顾客端通过联系客服处理。冲突核实跳模块 2，按同一审核项处理。成功撤回或跨店资格到期后立即停止跨店返回。记录与原件继续按 [03h §10](03h-customer-risk-feedback.md) 的受限留存和可见规则。

### 4.7 原单异常与客服核实

- **筛选**　先选门店再按原订单号／原业务编号、业务类型、问题类型、发生日期和核实结果查找。业务覆盖预约关联、洗护／美容／其他服务、寄养、商品、食品提醒或奖励兑换的原记录。平台补单前同时搜索可能已成功的订单。
- **列、状态**　门店、原业务／订单号、顾客或业务摘要、异常类型、服务／登记状态、最终应收、累计实收、已确认退款、最近处理结果。开单时间和实际款项发生时间分开。页签为待核实／可办理、已登记结果、已作废历史。查账默认读取原单与原流水。
- **详情**　订单摘要、服务或交付、商品与库存、款项、关联预约／原需求和时间轴。显示原金额和实际经办人。涉及商品时，同屏显示当前 SKU 的实际库存、预占库存、可售库存及取数时间，另列本单预占和本次操作影响的数量。提交前按服务端状态重验库存和预占；读取失败时展示待重试。
- **弹窗与结果**　「登记客服材料」「修改数据」「补录订单」「删除错误单」「登记补收」「登记消费退款」按 §6 逐项显示可用条件和提交前影响。普通金额录错提示门店回原单自助。食品及奖励自提内部备注在原记录上下文纠错，带前后值；商品超时补记库存冲突和停用遗留单从相应原单打开。所有已办理结果回同一原业务和日志。

### 4.8 积分实物与总仓履约

- **筛选**　「兑换与发货」按兑换单、奖励、领取店、兑换时间、履约状态；「奖励配置」按奖励名称与上下架状态。
- **列、状态**　兑换单、奖励、领取店、积分处理、发货与领取状态、发货时间与截止。履约状态为待总仓发货／已发往门店／已领取／已取消。区分真实领取与系统默认已领取。配置表显示名称、积分、平台库存、上架状态和可领取门店范围。
- **详情、弹窗**　「配置实物奖励」填写图、奖励、积分、库存、范围等 [03k §6](03k-customer-loyalty-points.md) 已定项；「确认总仓发货」核对原兑换、领取店、真实发货；「记录实物异常」在原兑换单登记错发、未收到等处理结果。
- **结果**　门店真实交付后登记领取。发货满连续 720 小时默认已领取且不退积分，展示系统来源、不填实际领取人或时间。领取店停用时按源规则自动取消并退回本次积分，顾客收重要通知。终态竞态只认首次合法转换，无人工强制取消、退分、改店按钮。补发等细分按业务待决范围收口。

### 4.9 广告与 AI 权益

- **筛选、列**　页签「启动封面广告」「首页底部 Banner」「养宠顾问权益」。广告按位置、环境、模式和启用／生效状态显示配置、有效期与更新时间；顾问按门店、权益状态和有效期查询，列出平台权益与门店开启状态。
- **详情、弹窗**　「预览与发布」或「停用」核对目标环境、素材／广告单元、有效期和当前发布版本；开启失败保留现行有效配置。Banner 照 [03o](03o-customer-home-banner-ad.md)；启动封面照 [03p](03p-customer-launch-cover-ad.md)，单次资源总等待最多 2 秒，自定义图片展示 3 秒并可随时跳过。首页顶部仍是门店栏。
- **顾问结果**　对指定门店授予、续期或停止已定养宠顾问权益，确认时展示门店和影响。门店决定本店是否开启，客户端按当前门店权益和原资格重验。广告配置独立于激励广告权益和顾客主动发起的一单一次 AI 洗护报告。收费契约与长期跨设备同步按 [03l](03l-customer-pet-advisor.md) 的待定和延后范围。

## 5. 次级页面

### 5.1 食品标准品牌归一

### 5.2 按门店导出数据

**入口**　「门店管理与资料审核 → 门店详情 → 导出本店数据」。一次锁定一个稳定门店编号，页头显示门店名称及编号。选择数据类别及适用的起止时间，可多选，生成一个分工作表的 Excel 文件。服务端从门店编号解析租户归属，逐表校验归属及字段权限。

| 类别 | 取数时间 | 工作表列与核对口径 |

| 财务 | 实际收退款时间 | 按真实资金明细逐笔导出，含原订单或充值编号、收款／退款类型、渠道、金额、实际发生时间及系统录入时间。消费、充值分表；消费净额取实收减已确认消费退款。 |

| 顾客／宠物 | 当前门店档案快照，界面明示时间 | 本店顾客编号、称呼、脱敏联系方式，宠物昵称、种类、品种及本店关联。 |

**边界**　按本店有效对象读取。证照／附件原件、完整手机号批量、顾客跨店风险、争议证据、未授权资产和凭据排除在首版导出列之外。财务保留真实 0 元免单与未收区别。下载限有效平台账号按当前权限取得其发起的文件，链接需重新鉴权。Excel 单元格使用明确类型，编号保留前导零，用户文本不按公式执行。生成／下载按所选门店、范围、结果和经办留痕。文件保留时长及容量上限在契约阶段登记。本入口属于平台后台，门店小程序继续在原统计与交易明细核对账目。

## 6. 原业务异常处理与直接修复

### 6.1 启用条件

**门店已停用，或店员端异常使这笔业务无法在原入口办理时，平台可直接修复。** 包括原单卡住、确认未落库、实际业务漏录和系统生成重复错单。门店用现有客服渠道说明情况；平台先读实际业务状态、版本和影响，记录异常依据（如原请求、客服核实或实际业务凭证）。已能自助的门店照常在小程序办理。平台确认一次即可提交，后台按等价业务动作校验，无门店二次审批。服务端不可办理或无法核实事实时，先在原异常登记，状态如实保留。

### 6.2 表单、结果与删除边界

| 动作 | 弹窗和输入 | 提交条件及双端结果 |
|---|---|---|
| 修改数据 | 核对原门店、原单、故障依据；并排显示改前／改后、影响的状态或金额 | 只展示原业务仍允许的字段和写动作。例如未结算商品的数量、允许变更的应收、普通备注及符合原规则的业绩归属。库存修改使用原调整逻辑，保留预占和变更记录；寄养照护与普通洗美结果按各自可改范围。写成功后双端读最新有效值。已结算金额和原财务事实沿原单追加记录。 |
| 补录订单 | 选择一个门店及业务，关联本店真实顾客或原散客关系、宠物／SKU、项目／数量、发生时间和既有预约／需求；填写实际业务及款项证据，确认本单应收及经办归属 | 已有有效原单时跳回原单。确认缺单才创建一张标准订单。使用原业务检查、服务状态、库存与收款约束，有真实发生且可核实的才登记在对应状态；真实收款按实际发生时间，系统录入保存现在时间，未实际付款显示未登记。缺少顾客绑定时按原可见规则，不能派给同名、同号他店顾客。记录实际平台操作者，与原店员归属分开。 |
| 删除错误单 | 确认框展示门店及订单号，逐项检查款项、服务／交付、库存、券／余额／积分、关联原业务，展示作废后的可见性及原历史留存 | 只允许作废尚无真实服务或交付、收退款或免单、已落账库存及权益变动，并满足原取消条件的错单。纯预占按原取消同次释放，无法安全解除关联则保留原单转核实。沿原取消状态移出待办与正常列表，归档从操作历史查询；顾客如已收到原单链接且仍有权查看，按原规则显示已取消。已产生业务或账务事实的订单，按原业务条件处理取消、退货或补收／退款，历史保留。 |
| 登记补收／消费退款 | 原单同时显示最终应收、原实收及渠道、已退、可核实的差额／可退上限、本次金额、实际发生时间；凭证随原单，退款原因必填 | 复用 [03d §11.3、§12](03d-customer-orders.md) 与 [03c §5.1](03c-customer-wallet.md)。已线下收款漏记只补实际差额，顾客不用再付。真实退款按原渠道和上限登记，钱包按原本金／赠送拆分规则处理；无真实款项先登记差错事实。原实收、拆分、钱包流水等已记账原事实锁定。退货是否回库按实际收回且可售决定。 |
| 登记核实材料／结论 | 原记录与故障、来源、结果或关联处理记录 | 处理 24 小时超时商品补记库存冲突、食品风险／奖励自提内部备注误填、停用店遗留单。商品按 [03e §13.1](03e-customer-products.md) 关联原需求，库存不足或无法核实则仅登记，不恢复原需求或写半笔销售。备注按原提醒／兑换单做更正，保留改前改后和可见范围。 |

### 6.3 一次提交、事实留痕与回写

- 读写以原商户和门店真实关系为准。提交前重验同类原单、稳定请求、服务／订单版本、资金、预占、券、库存和当前门店可操作状态。店员恢复后与平台同时提交，以首个合法写入为准；网络未知时先查同一请求结果。失败不留下半笔流水、孤立扣库存或假状态。
- 补单对照同一预约、购买需求、故障原请求或能唯一确认本店本次成交的原凭据。平台和门店提交不同请求时也按原业务关联核对。合并转账分别对应各单份额，付款引用相同或顾客同日再次消费均不能单独作为重复订单依据。发现同笔钱包款已记账时核对原流水，原业务允许关联时才补齐缺失记录。结果未知或关系无法唯一核实时先核实，避免重复扣款。
- 补录和改删走原业务规则及 [字段注册表](FIELD-REGISTRY.md)，复用已有对象归属、幂等和审计。订单、资金和服务的真实发生时间与后台操作时间分别展示。记录故障依据、原单或候选、动作前后、受影响的关联记录及实际平台账号。既有必填项沿源业务，操作日志自动生成。
- 店员端从业务原列表、原单或已结束历史查看有权结果，正常店员操作仍走原入口。客户端仅在其原订单／服务／消息范围读真实结果；按原业务触发通知，重试不重发，内部原因和后台原始日志不外露。已确认顾客不可见的风险记录继续按 §4.6 执行。
- 首版使用业务按钮和已登记字段，禁止任意表／字段编辑、复制他店记录、物理删单及直接覆盖原钱包、回写虚假历史。已生成的 AI 洗护报告按原规则保留，补图只更新对比展示。

## 8. 发布分批、非目标与开工边界

先完成双端核心验收，再用对应的真实业务记录验收 Web。模拟 Web 管理页面不可用时保持双端业务接口可用，验证高频业务继续走原流程。依赖平台处理的场景，随对应小程序功能实测平台动作和双端回写后开放。

| 阶段 | 范围与接入条件 |
|---|---|
| 先验收双端核心 | 用一人门店验收预约确认、洗美、寄养离店结算和商品成交。店员从店员端操作，顾客从客户端查看对应结果。 |

| B · 随场景上线 | 消费争议、食品风险及顾客风险，分别随小程序功能启用对应处理与真实回写。品牌归一随食品风险。 |
| C · 随运营模块上线 | 积分实物发货及原单异常、广告、养宠顾问权益。完整平台后台及批量运营继续后置。 |

依赖平台的场景在对应按钮、权限与结果回写可用后开放。阶段范围以[状态文档](REQUIREMENTS-STATUS.md)为准。首版非目标是门店 Web 收银与进销存、跨业务混结、线上代收、批量修改／删除和重新开发完整营销／分销／团购。历史订单批量导入、AI 聊天长期跨设备同步及低频边缘处置按各模块阶段或人工承接。

UI 可按章节制作首页、表格、详情、确认弹窗与状态稿。研发可按动作映射设计契约，后端复用现有业务动作及逻辑字段。账号发放、会话参数、对外服务时效、导出文件留存和动作接口在阶段 08／09／11 完成；新字段先登记。正式编码和发布的准入继续读[执行标准](execution/deepseek-execution-standard.md)。

| 1 人门店与 Web 故障隔离 | 预约确认、洗美办理、寄养实际离店结算、商品销售均可在店员小程序完成，顾客只看本人真实结果。Web 管理页面不可用且业务接口正常时，再跑四条路径仍通过。 |
| 登录与待办 | 两个账号能力相同、日志可区分实际经办人，失效会话拒绝访问；每张卡与跳转列表计数一致。 |
| 资料审核与账号异常 | 撤回和通过仅一个成功；生效后双端同版本且证照保密；账号冲突保留原身份与历史。 |
| 门店停用 | 六项清单均可查原记录，来源失败与 0 条可区分。喂养接续和奖励退分依各自规则。 |
| 争议、食品与顾客风险 | 7 天回应和 3 天补证读取真实截止；裁决、解决确认、厂家回信、门店知悉和顾客风险授权互相独立。 |
| 按门店导出 | 建两店同名顾客、同名商品与不同交易。文件只含选择门店，订单／财务日期口径正确，快照和流水可核对，实际行数与工作表相符。换店、生成失败、越权下载、过期和空结果有准确提示。 |
| 异常改数据与补单 | 商品改单卡住时，同屏显示对应 SKU 的实际、预占和可售库存，平台修改后正确调整原预占。漏单核实后只补一次，已有钱包扣款不重复扣。店员恢复并发或平台重试均不重做。 |
| 异常删错单 | 无款项、无服务记录的重复单可作废，纯预占只释放一次、审计可追溯。已有实收、已核销券、已出库或有服务事实时直接删除拒绝，返回原业务处理入口。 |
| 原单真实补收／退款 | 实收 100 元只记 80 元且凭证核实时，原单补登 20 元；门店正常时走自助，确实无法自助时平台代办。退款按原渠道和额度，减一次业绩。 |
| 商品、奖励与权益 | 商品实际成交超时补记遇库存冲突不写半笔；积分超期默认领取与停用退分只成功一次；广告、顾问权益变更在正确门店和环境生效。 |
