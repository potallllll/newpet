# 阶段 08｜双端接口与鉴权验收

已运行的 OpenAPI 与请求结构测试见[验证记录](08-contract-verification.md)。行为、鉴权、数据库联动、微信和 Redis 行列为正式联测用例。样例用合成数据，验证时取服务端真实 request_id、对象版本、审计和最终业务事实。

| 用例 | 执行动作和前置 | 预期接口结果与业务事实 | 验收层 |
|---|---|---|---|
| AUTH-01 | 游客浏览门店项目与商品，再尝试读个人宠物或订单 | 首类允许且无电话敏感字段/证照/库存实数；个人数据 401 | HTTP |
| AUTH-02 | 同一 User 在顾客和店员小程序申请访问；用顾客受众 token 调门店接口 | 共用稳定 User，顾客 token 不能执行店员接口；本店当前有效人员可正常办理 | HTTP / 微信测试号 |
| AUTH-03 | 登录微信但尚未核验手机号；拿预认证挑战读业务 | 只得到 mobile_required 和短期挑战，业务接口 401 | HTTP / 微信测试号 |
| AUTH-04 | 验真新微信同手机号后请求换绑；不确认、确认、旧请求重放 | 未确认不改原绑定；确认只迁移一次，旧双端会话立即不可用，原身份/历史/钱包保持 | HTTP / 微信测试号 / DB |
| AUTH-05 | 新微信已绑定另一个有业务历史账号，或缺可靠跨端对应证据 | 返回明确冲突或能力暂不可用；不合并或转移原账号资产 | HTTP / 微信测试号 |
| AUTH-06 | 两个用户竞争一张入职邀请；已加入者重复点击 | 合法先成功者加入；另一位拒绝；原邀请只消费一次，换绑不自动入职 | HTTP / DB |
| AUTH-07 | 停用并恢复某店员；分别请求原店员会话、本人顾客会话和新店员会话 | 停用后原店员会话失效；恢复后旧会话不回生；顾客权限保持当前合法范围 | HTTP / DB / Redis |
| AUTH-08 | 店 A 员工读店 B 对象，用同店订单搭对方的结算、退款、宠物、钱包、SKU | 各组合都不可访问，越店及不可见对象不回显真实存在或内部 ID | HTTP / DB |
| AUTH-09 | 顾客把自有和他人宠物混入批次；店员给未绑定顾客指向主人宠物 | 整批拒绝，保留原事实；本地未关联宠物仍可使用 | HTTP / DB |
| AUTH-10 | 有效员工读老板管理、改他人称呼、改他人归属订单 | 权限不足；本人称呼可改，只有老板能更正其他合法归属 | HTTP |
| AUTH-11 | 身份库或 Redis 中断；再测试旧缓存 | 私有写不凭旧角色通过；公开投影按允许策略降级；业务已提交结果可恢复 | HTTP / Redis |
| APP-01 | 顾客创建洗护申请，门店确认，预约转单、开工、完成、收款后顾客回看 | 当前有效预约一条、原服务一条（每宠），财务动作前未收款，顾客得到本人真实事实 | 双端 / DB |
| APP-02 | 同时提交多笔同一时段预约，再关闭该时段；提交或改期两端刷新 | 无时段名额拒绝；非营业新申请和改期按最新版本失败，老承诺不静默消失 | HTTP / DB |
| APP-03 | 到预约提前 6 小时整时发改期；未开始按授权发取消 | 改期不允许；取消沿独立业务条件办理 | HTTP / DB |
| APP-04 | 原有效预约改期待确认时，门店开始服务与对方接受新提议同时发生 | 原版本只允许一条合法路径，一次成功且保持批次一致 | HTTP / DB 并发 |
| APP-05 | 在快开中匹配同店同次有效原预约，从提示转单，再从会员快开处理另一次 | 原单不重复；不同真实到店才可另开，快开先完成必要检查并进服务中 | HTTP / 双端 |
| APP-06 | 拒绝一条待确认申请；另一条任其超时；第三条已确认到时后先刷新，再由店员核实未到店 | 三条 V001 状态分别为 rejected、expired、cancelled；第三条核实前仍 confirmed，核实后返回 no_show；每条终态都无有效提议，无重复业务记录 | HTTP / 双端 / DB |
| APP-07 | 对原已确认预约分别由门店、顾客发起有效改期；拒绝或让其过期 | 分别返回 awaiting_customer 和 awaiting_store，V001 保持 confirmed，原时间和项目不变；提议关闭后回 confirmed | HTTP / 双端 / DB |
| SVC-01 | 洗美缺一检查、异常未记录主人决定、正常无图，分别提交 | 前两种拒绝；正常无图合法；全身仅照片位 | HTTP / 双端 |
| SVC-02 | 同宠洗美加护理，再尝试复制造一个独立服务 | 计价行保留，沿同一进度与原检查，重复服务拒绝 | HTTP / DB |
| SVC-03 | 中止后试图重启原单；正常完成后补照片与普通文字 | 中止不复活；普通补改成功，不通知、不变价或重跑报告 | HTTP / 事件 |
| SVC-04 | 顾客同时发起两条原订单 AI 报告请求，重复提交旧回调 | 真实资格仅使用一次，一个成功报告，补图和旧回调不覆盖；未开放时真实显示能力不可用 | 广告/AI 后续联调 |
| BRD-01 | 两只不同日价宠物各自入住，A 先离店挂单，B 仍在住 | A 按实际时间截止计费，B 仍在住；A 原批可收款，顾客状态正确 | 双端 / DB |
| BRD-02 | 分别测试 03:00 入住、03:00 离店、零晚；反复确认同一宠物同一批 | 入点排除、离点包含，零晚基础费为零；同宠不重复离店收费 | HTTP / DB |
| BRD-03 | 将未收款离店时间更正为晚于首次确认；再试未来时间、早于入住，以及收款后更正 | 合法更正调整晚数与应收，首次确认保留；其余拒绝，账本不覆盖 | HTTP / DB |
| BRD-04 | 结清或主动解除一批挂单，分别查未解除、已解除和欠款 | 历史挂单按原时间可查；主动解除不结清欠款，收款结清不变离店事实 | HTTP / DB |
| BRD-05 | 顾客在寄养中提交加餐与照护查询；尝试他人寄养、离店或无权限附件 | 有效原单关联的加餐走商品；非法请求拒绝，私密照护不返回 | HTTP / DB / 媒体 |
| PAY-01 | 应收 80.00，钱包 30.00 和现金 50.00，另外尝试第三种、金额不符和重复渠道 | 首例一次结清；不合法组合拒绝。钱包本金再赠送，顾客未看到内部支付拆分 | HTTP / DB |
| PAY-02 | 只调应收 0.00，再明确确认免单；重复请求和夹杂旧收款 | 只调价未结算；明确免单且原因有效才提交，无虚假付款，适用出库/用券一次 | HTTP / DB |
| PAY-03 | 同一笔线下凭证分摊两单，再提交总计超出；结清后直接改实收与真实补收 | 只允许原单真实分摊；超额拒绝；原应收与原实收锁定，合法补收独立追加 | HTTP / DB |
| PAY-04 | 草稿保存退款，两个员工确认同一额度，再试未付款渠道与任意钱包入账 | 草稿无资金；并发结果不超剩余额度；严格原渠道/原组成退回 | HTTP / DB |
| PAY-05 | 将优惠计入应收后重试改价、换券、退款，多单统计汇总 | F-ORD-013 严格等于最终减原始；优惠只记一次，已核销券不因退款恢复 | HTTP / DB |
| PAY-06 | 用正确版本、锁定应收 80.00，收款请求却按 70.00 断言且拆分合计 70.00；之后用正确应收和拆分重试 | 首次 409 RECEIVABLE_AMOUNT_CONFLICT。应收、付款、钱包、库存、券和版本无变更。重新核对后按锁定应收收款一次 | HTTP / DB |
| PAY-07 | 录入一笔昨天已线下退款的消费退款。分别省略 refunded_at、传无时区值、传带时区的昨天实际时间 | 前两种 400，无退款流水；最后一次按实际发生时间入账，服务端审计时间独立保存 | JSON Schema 已验请求；HTTP / DB |
| WAL-01 | 仅赠券充值，依次无备注、空白、有备注并重复相同请求 | 无备注/空白不入账不发券；合法到账和发券各一次 | JSON Schema 已验请求；HTTP / DB |
| WAL-02 | 分别以原赠送金已用、原赠券已用、两项均未用造三笔充值；使用店员和老板分别提交 standard 及 owner_manual | 任一已用时两角色提交 standard 均为 409 RECHARGE_REFUND_OWNER_MANUAL_REQUIRED，无资金变化；店员提交手动为 403。本店老板在已用时手动且金额合法才成功，只扣本金；无已用时老板手动得 422，标准分支按原规则收回合规的未用权益。金额或余额不足均拒绝 | HTTP / DB |
| WAL-03 | 同一认证用户查 A 店、B 店钱包；试读他人的钱包流水 | 本人两店各自独立，并可见本人本金和赠送余额；他人流水不可读 | HTTP / DB |
| WAL-04 | 模拟原赠送金消费或赠券核销与 standard 退款同时提交；另测同一次退款请求重放 | 原数据竞争结果与提交顺序一致，先使用时 standard 拒绝，未使用权益已合法回收后无法再用；同次退款最多入账一次 | HTTP / DB 并发 |
| CPN-01 | 双请求一单锁两普通券／一券锁两单，尝试锁过期券及换券失败 | 只取得合法唯一锁；有效期不延长；换券失败回滚原合法锁，未结算不核销 | HTTP / DB |
| CPN-02 | 本店码两人争兑，72 小时顺延；月末兑换后查看期限，其他门店尝试 | 只兑一次；兑换与 1 个日历月两种截止准确；越店不可兑；不会自动开订单 | HTTP / DB，凭证策略通过后 |
| CPN-03 | 老板和店员分别用统一券模板接口查省略、active、disabled、all；用另角色或不同筛选的游标再查 | 省略或 active 只见本店可发模板，disabled 和 all 只有本店老板能查，店员得到 403。游标不能扩大权限，停用模板不可新发，已发券继续按实例快照使用 | HTTP / DB |
| SKU-01 | 同 SKU 加购物车至最后一件，两个请求同时确认；结算/超时释放竞态 | 购物车不扣，确认只有一笔可预占，之后只销或释放一次，超量不产生负库存 | HTTP / DB |
| SKU-02 | 对商品登记退款；再登记实际收回有一件可售；同键和新键重复 | 退款本身不回库，真实可售回库一次，按原SKU和数量约束 | HTTP / DB |
| SKU-03 | 同图入库时提示，第一次手工确认后提交旧表单，设库存低于预占 | 重复图只提醒，原已入库不能二次入库，库存低于预占拒绝 | HTTP / DB；识别能力另验 |
| TECH-01 | 请求已提交后断线，用同键同内容、同键不同内容、旧版本、过期身份重试 | 还原原结果，冲突 409，旧版本提示重查，旧身份不能重放获取数据 | HTTP / DB |
| TECH-02 | 正常业务提交后模拟消息未投递，重放已完成事件 | 业务原账本不动，消息最多一条可见结果、原业务处理不停；仅普通/重要 | HTTP / DB / Redis |
| TECH-03 | 私有媒体拿到旧 URL、跨店或非本人附件、营业执照无权限 | 重新签发时按当前授权拒绝，超期签名失效，公开详情永远不含证照 | HTTP / 对象存储 |
| TECH-04 | 阶段 05 平台不可用，或测试号缺广告/微信通知能力时跑核心 | 门店非依赖操作继续正常；故障能力展示真实状态；核验申请不可伪装成已通过 | 双端 / 部署 |
| TECH-05 | 提交预约拒绝、调价等选填原因为省略、null、空串或全空白，并在成功后重放同键同规范化请求 | 合法动作均通过，服务端将空原因保存为 NULL，同键不重复写。消费退款、充值退款、免单的空原因失败 | JSON Schema 已验请求；HTTP / DB / 幂等 |

通过证据建议包含前后状态、拒绝码、收到请求的真实身份及 V001 事实。状态改变接口须查接收方新视图及可见项，命中 200 本身无法证明整个双端流程成功。
